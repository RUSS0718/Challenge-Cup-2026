## 1024-token 详细分析

### 正确题 (12/23)
idx 3,4,5,7,8（受控算术 L0）+ idx 11,13,14,16,17,18,21

### 错误题 (11/23)
- idx 0,1,2：原始样例（抽象代数/测度积分/复分析）— 即使 1024 token 仍错误
- idx 6：受控算术 `(45-9)/6+4` — 应该是 L0 路径，需排查
- idx 9,10：代数方程 — 多解格式问题
- idx 12：等差数列 — 模型求解错误
- idx 15：概率 — 计算错误
- idx 19：定积分 — 提取或计算问题
- idx 20：复数 — 提取或计算问题
- idx 22：GCD — 格式指令污染，1024 token 仍无效（P0.2 已诊断）

### 关键指标改善
- 候选拒绝率从 60.9% → 4.3%（仅 1 题有候选被拒）
- 全候选拒绝从 1 题 → 0 题
- 所有 23 题均有非空最终响应
- 0 次请求超时
- within_call_cap=True

## 决策：KEEP 256（默认）

**否决原因**：1024-token 配置虽然准确率翻倍（12/23 vs 6/23），但 **645 秒总耗时超出 600 秒预算（Gate #3 FAIL）**。

复评跳过：1024 已未通过 Gate #3，无需进行两次复评。512 未通过 Gate #1（准确率 3/23 低于基线 6/23），同样无需复评。

## 核心洞察

1. **输出 token 预算是最强约束**。从 256→1024 带来的准确率提升（+26.1pp）远超任何其他已测变量（调用数扫描最多仅噪声波动）。
2. **当前架构不是瓶颈**。同样的 6-call/3-candidate 架构在 1024 token 下表现翻倍，说明架构本身能承载更高准确率。
3. **三个原始样例仍是硬骨头**。idx 0-2 在 1024 token 下仍错误，需要更强的推理能力或 Prompt 优化。
4. **P1 最高收益方向**：在不增加总耗时的前提下提高输出质量——Prompt 优化使模型更快收敛到答案，而非单纯增加 token 上限。
