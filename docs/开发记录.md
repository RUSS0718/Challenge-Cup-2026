# 开发记录

## 2026-07-25

- 基线修复：恢复 `user_agent.py` 和测试文件中的 UTF-8 文本与语法；使用 `C:\Users\CQX\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe` 作为本地可用解释器，不依赖 Windows Store `python.exe` 别名。
- 答案处理：实现无模型调用的嵌套 `\boxed{...}`、中英文答案标记、选择题和末行回退；将常见分数、小数和根式做保守规范化。`1/2`、`\frac{1}{2}` 和 `0.5` 会聚类；未知表达式保留为原字符串的规范文本。
- 候选与审核：候选显式保存 `answer`、`normalized_answer`、`evidence`、`verification_status` 和 `model_calls_used`。选择顺序为受控工具证据（当前未接入）→ 答案共识 → LLM 审核 → 固定候选 ID。审核只要求首个可证实错误和短 `VERDICT`，trace 不保存 prompt 或模型原文。
- 本地评测：`scripts/evaluate_dev.py` 不向 `solve` 传入样例 `answer`，并输出准确率、调用数、延迟、超时数、空响应数和失败题目 ID。默认单请求超时为 30 秒、重试 1 次，可用 `--timeout-seconds` 和 `--retry-count` 调整；这是本地诊断配置，不影响官方 client。
- SymPy 实验：新增独立 `sympy_adapter.py`，只接受受 AST 白名单约束的整数/符号算术，不执行模型 Python、不访问网络/文件或启动子进程。仅在 `AgentConfig(enable_sympy_evidence=True)` 时，简单算术题会用独立表达式重算候选答案并生成 `controlled_tool` 证据；默认链路不调用它，也不会用它覆盖答案。适配器只能报告执行后的软超时，禁止子进程意味着它不能宣称进程级硬超时。
- 验证：使用 `.venv\Scripts\python.exe` 安装已声明的 `sympy` 后，`py_compile` 与 22 项单元测试通过。开发集 CLI 以 2 秒请求超时、1 次重试、20 秒总预算运行，A/B 报告分别保存为 `docs/development_baseline_a_2026-07-25.json` 与 `docs/development_baseline_b_sympy_2026-07-25.json`。
- A/B 结论：两组均为 3 题、准确率 0、平均 3 次调用、约 6.37 秒/题、3 次超时、0 个有效模型响应。该结果只证明当前 API 超时，不能证明 SymPy 有收益；默认接入条件尚未满足。
- 被拒绝方案：未接入 LangGraph、常驻服务、任意 Python 执行、Lean 或 SymPy 默认路径。仅当固定开发集 A/B 显示稳定收益且成本可接受时，才评估将受控适配器接入默认链路。

- 候选选择审视：当前实现只降低 `REFUTED` 候选的排序，尚未实现方案文档所述的确定性淘汰；因为有效开发集基线仍未恢复，未将该行为变更接入提交路径。待基线恢复后，先补充“存在未被反例否定候选时不选 `REFUTED`”的测试和 A/B，再决定是否合入。

- 依赖验收：使用独立临时虚拟环境从精简后的 `requirements.txt` 安装后，23 项单元测试与 `py_compile` 全部通过。
- API 诊断：`chat.intern-ai.org.cn` 的 DNS、TCP 443 和 TLS 握手均成功；以 5 秒单请求、1 次重试、30 秒总预算调用默认 Chat Completions 端点时，前两题各三次请求均分类为 `timeout`，第三题因总预算未启动。当前证据只能定位为 HTTP 请求/上游处理超时，不能区分服务端限流、排队或模型处理；冻结基线和 SymPy A/B 因此仍待 API 恢复后重跑。
- 延迟修复与有效基线：实测确认真实数学提示配合 `max_tokens=4096` 即使等待 45 秒仍超时，而相同提示使用 256 可正常返回，因此将默认生成上限固定为 256，并新增回归测试。以 15 秒请求超时、1 次重试、90 秒总预算重跑的默认基线已写入 `docs/development_baseline_2026-07-25.json`：3/3 题均有有效响应、无超时、平均 6 次调用、平均 19.275 秒，但准确率为 0。
- SymPy A/B：同一配置下，`--enable-sympy-evidence` 的报告已写入 `docs/development_baseline_b_sympy_2026-07-25.json`。三题均不符合受控简单算术输入范围，未生成工具证据；无超时、平均 6 次调用、平均 18.879 秒、准确率仍为 0。样本过小且无准确率增益，适配器继续保持默认关闭。
- 审核与证据裁决：等价答案现在按答案组只审核一次，审核结论在组内共享；三态比较仅在能证明相等时返回 `EQUIVALENT`，数值或选择项可证明不同时返回 `NOT_EQUIVALENT`，其余表达式返回 `UNKNOWN` 并分组隔离。存在未被反例否定的候选时，`REFUTED` 候选不再凭共识优先选中。相关单元测试通过；开发集对照 `docs/development_baseline_grouped_audit_2026-07-26.json` 无准确率或调用数变化，因为每题的三次生成均未形成等价组且默认未启用工具证据。
- 动态预算与局部修正：实现了默认关闭的 `--enable-dynamic-budget` 与 `--enable-local-repair` 实验开关。动态路由对简单受控算术使用 L0（1 次生成、至多 1 次审核），其余问题使用 L1（至多 2 次生成）；修正仅在审核明确失败时重写受影响候选并复审，且受 `max_repairs` 与总模型调用预算限制。动态预算对照 `docs/development_baseline_dynamic_budget_2026-07-26.json` 将平均调用从 6 降到 4、平均延迟从 19.275 秒降到 13.450 秒，但 3 题准确率仍为 0；局部修正对照 `docs/development_baseline_local_repair_2026-07-26.json` 未触发修正、准确率为 0 且平均延迟升至 25.485 秒。冻结集太小且没有正确样本，二者均不进入默认路径。
- 解析覆盖：方程、集合、区间、向量与矩阵形式的最终答案标记提取均已加入单元测试。该覆盖只验证保守提取，不宣称已完成这些类型的完整数学语义解析。
- 扩展开发集与 A/B：`sample_data/dev.jsonl` 已扩至 23 题（保留 3 道原始样例，新增 20 道标记为 `local_handcrafted_2026-07-26` 的本地调试题）。新增题覆盖 6 道严格受控算术、多解方程、易错计算与不同题型；它们不是隐藏评测题，`answer` 仍只由 `scripts/evaluate_dev.py` 在本地评分时读取。以 15 秒请求超时、1 次重试、480 秒总预算执行的默认报告为 `docs/development_baseline_expanded_2026-07-26.json`：23/23 有最终响应，1 次请求超时，解析失败率 0，平均 5.565 次调用、17.443 秒，但准确率为 0。
- 观测与结论：评测报告新增 `answer_not_extractable_rate`、受控工具调用、答案组审核和修正尝试计数。SymPy 对照（`docs/development_baseline_expanded_sympy_2026-07-26.json`）实际产生 35 次工具检查，准确率仍为 0；默认关闭。动态预算对照（`docs/development_baseline_expanded_dynamic_budget_2026-07-26.json`）将单次观测中的平均调用和延迟降为 3.348 次、10.923 秒，但准确率仍为 0；尚未重复运行，因此不满足“可复现收益”门槛，默认关闭。局部修正对照（`docs/development_baseline_expanded_local_repair_2026-07-26.json`）修正尝试为 0，无法评估收益，默认关闭。默认报告的 59 次答案组审核低于 23×3=69 的未去重上限，说明本轮确有 10 次审核被去重；这只是调用量观测，不证明正确性收益。
- 归档与边界：`docs/development_baseline_a_2026-07-25.json` 已标记为 `superseded_timeout_only`，应使用有效冻结基线或上述扩展报告。未恢复大于 256 的输出上限，因此不执行新的高 token 延迟试验；L2 路由和对 `uncertain` 的修复尚无真实收益证据，仅以默认关闭的实验开关实现，未进入默认路径。
- P2 候选演进：新增默认关闭的 `enable_l2_routing`。在动态路由的非 L0 路径中，两个初始候选形成不同答案组时才升级为 L2，补充 1 次生成；该实验路径使用显式 `l2_max_model_calls=8` 硬上限，L0 与默认路径仍使用原有上限。新增默认关闭的 `enable_uncertain_repair`：仅在没有任何审核通过候选且候选状态为 `uncertain` 时，按既有 `max_repairs` 上限尝试一次局部修正并复审。两条路径都有触发与不触发的单元测试，且 trace 不保存模型原文。
- P2 对照：`docs/development_baseline_expanded_l2_2026-07-26.json`（动态预算 + L2）在 23 题中实际升级 13 次，平均 4.174 次调用、13.561 秒，准确率 0；相对动态预算对照没有正确性收益且成本更高。`docs/development_baseline_expanded_uncertain_repair_2026-07-26.json`（动态预算 + 局部修正 + uncertain 修复）实际修正 4 次，平均 3.609 次调用、11.181 秒，准确率 0；相对动态预算对照同样没有正确性收益且成本更高。两项保持默认关闭。评测脚本同时修正为只把 skipped/rejected/fallback/not_run 步骤的原因计入失败原因，正常的 `answer_conflict` 路由不会污染失败统计。
- 2026-07-27 根因与默认修复：`docs/development_failure_diagnosis_2026-07-27.json` 对 23 题逐题给出失败分类与一句依据。256 token 的原始本地抽样显示模型在输出最终答案前持续生成冗长推理，且常回显输出占位符；答案优先短提示在 6 道基础题上仍为 0/6，因此被拒绝。新增严格受控算术 L0 路径：1 次生成申请 1024 token，其余题仍固定 3 次、256 token。基础题两轮 256 均为 0/6，1024 为 3/6、6/6；完整 23 题两轮均为 6/23、无超时（平均 3.913/13.250 秒和 3.870/12.863 秒），因此 `enable_l0_extended_tokens` 默认启用。
- 2026-07-27 实验复评：动态预算两轮虽降至 2.826/9.978 秒和 2.652/10.266 秒，但准确率为 5/23、3/23，低于默认 6/23，保持关闭。SymPy 复评产生 20 个工具步骤：4 `SUPPORTED`、0 `REFUTED`、2 `UNKNOWN`、14 不适用，准确率 4/23，保持关闭。局部修复在非零默认基线上仍为 0 次触发、5/23，保持关闭。L3 未实现：已确认当前瓶颈是输出长度与格式回显，缺乏引入更复杂编排的必要性。
