# P0.1 token 阶梯实验报告

日期：2026-08-13

## 目的

官方评测暴露 1024 token 截断（~98.7% finish_reason=length）是 0 分与系统负载终止的根因。P0 止血版本已把路径压缩为「单次主调用 + 至多一次条件重试」，本实验在 1536/2048/3072 三档上确定满足 Gate 的最低成本 token 上限。

## 方法

- 新增 `llm_client.InternChatClient.finish_reasons`：本地诊断 client 在成功返回前记录 `choices[0].finish_reason`，不改变 `chat -> str` 契约。
- 新增 `scripts/evaluate_token_ladder.py`：串行/并发跑 112 题冻结回归集，按题切分主调用/重试的 finish_reason，输出 length 率、答案标记覆盖率（1 − 条件重试率）、非空率、平均/P95/总调用、准确率，以及 `gate_check()` 的 Gate 1/2 判定。
- 新增 `tests/test_evaluate_token_ladder.py`（4 项）。

### Gate 定义

- Gate 1（资源/接口）：非空 final_response = 100%、总调用 ≤ 224、平均调用 ≤ 1.5、invalid ≤ 2%。
- Gate 2（长度）：主调用 finish_reason=length ≤ 20%（硬门槛，目标 10%）、答案标记覆盖率 ≥ 95%。
- Gate 3（准确率）：选定档位双轮独立复评可复现。

## 结果（干净数据）

| 档位 | 主调用 length 率 | 答案标记覆盖率 | 准确率 | 平均调用 | 总调用 | fallback | Gate 1 | Gate 2 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- | --- |
| 1536 | 53.6% | 88.4% | 67.9% (76/112) | 1.12 | 125 | 13 | ✅ | ❌ |
| 2048 | 35.7% | 96.4% | 75.0% (84/112) | 1.04 | 116 | 4 | ✅ | ❌ |
| 3072 第1轮 | 10.7% | 99.1% | 81.2% (91/112) | 1.01 | 113 | 0 | ✅ | ✅ |
| 3072 第2轮 | 17.9% | 97.3% | 80.4% (90/112) | 1.03 | 115 | 0 | ✅ | ✅ |

- 准确率单调递增：67.9% → 75.0% → 80.8%（3072 双轮均值）。
- 仅 3072 通过 Gate 2：length 率降到 20% 硬门槛以内，答案标记覆盖率 ≥ 95%。
- 3072 双轮复评：81.2% / 80.4%（91 / 90 题正确），0 fallback，可复现性通过 Gate 3。

## 决策：ADOPT 3072

`AgentConfig.max_tokens` / `l0_max_tokens` 默认值从 2048 改为 3072（`user_agent.py`），README 默认配置表与测试断言同步更新。全量 163/163 通过。

### 不测 4096 的理由

- 3072 已满足 Gate 2 硬门槛（两轮 10.7% / 17.9% 均 ≤ 20%），不属于「前面仍大量截断」的情形。
- 关键：length ≠ 无答案。3072 即便第二轮 length=17.9%，答案标记覆盖率仍 97.3%——模型在截断前已写出「最终答案：」标记，final_response 是紧凑规范化答案，不受推理文本截断影响。
- 4096 有历史延迟/超时风险，且准确率已进入 80%+ 平台，再升 token 收益有限。

## 过程教训（限流）

- 并发 8 跑 1536 触发 API 限流：请求快的档位（1536 单题 ~8s）在并发 8 下快速连续发请求，大量 429 快速失败，`finish_reason` 缺失约 168/198，准确率被严重低估到 17%（干净数据实为 67.9%）。
- 修复：低并发（1536→3、2048→4、3072→6）+ retry=3 退避 + 每档单独跑。重跑后数据完整（finish_reason 全量、lat 回到正常 14–21s）。
- 结论：本地大规模评测必须按「请求速率」控制并发，不能只看「题目数」。请求慢的档位可高并发，请求快的档位必须降并发。
